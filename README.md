# 低温联锁规程 · 离线补传协同确认服务

两台维护终端离线编辑《低温联锁规程》后补传补丁，服务端为批准文本维护**随确认补丁演进的
稳定字符标识序列**，终端在已批准全文上选择插入点/删除片段后以**两端锚点**受保护补传；
并发改动后按当前标识序列定位并原子确认，锚点失效时明确拒绝。旧式无锚补丁、幂等重传及
历史变换结果全程兼容。

## 功能与规则

### 终端侧（页面）

- 在已批准全文上：光标置于两字符之间 →「记录插入点」；拖选连续片段 →「记录删除片段」。
- 页面只保存**选择所见修订与两端字符锚点**（localStorage，含本终端补丁标识）；
  刷新或服务重启后，锚点的当前位置与最近结论**只从接口恢复**（`seq` 与 `lastConfirmed`），
  本地旧草案仅标注为“未批准”，绝不当作已批准内容。
- 补传成功后只显示服务端确认的**全文、修订与实际落点**；被拒绝时提示具体原因，文本与修订不变。

### 服务端

- **建立草案**：`POST /api/documents` 建立规程草案（修订 0）。
- **读取当前全文与锚点序列**：`GET /api/documents/:id` 返回全文、当前修订、
  稳定字符标识序列 `seq: [{id,ch}]` 与最近确认结论 `lastConfirmed`。
  **任何时刻 `seq` 拼接文本恒等于当前全文**（单测与验收均断言）。
- **提交补丁**：`POST /api/documents/:id/patches`，支持两类载荷：

  旧式无锚补丁（历史接口完全兼容）：
  `{ id, baseRevision, op, pos, text? | len? }`

  受保护补丁：
  `{ id, protected: true, op:"insert"|"delete", leftId, rightId, text, baseRevision? }`
  - 插入：`leftId/rightId` 为插入点两侧相邻字符标识（文首/文末传 `null`），`text` 为插入内容；
  - 删除：`leftId/rightId` 为目标片段首、尾字符标识，`text` 为选择时所见片段内容。

- **迟到补丁转换**（旧式）：依次转换越过 `baseRevision` 之后的每条已确认补丁：
  - 同位置插入按**补丁标识字典序**定序（小者在前）；
  - 插入落在删除区间内 → 插入保留，落点收敛到区间起点；
  插入点落入删除区间 → 删除拆为两段，插入文本保留；
  - 重叠删除 → 仅删除未被对方覆盖的部分（可能拆段或成为空操作）；
  - 以上情形均为确定结果，两份并发补丁**无论提交先后均收敛到同一文本**。
- **受保护补丁的接受与拒绝**（按当前标识序列定位，校验通过才原子确认）：
  - 接受条件：插入的两端锚点仍**相邻**（仍围住原选位置）；
    删除的两端锚点之间（含端点）当前内容与选择所见 `text` **完全一致**（连续且内容未变）。
  - 拒绝（均为 409，且**文本与修订不变**）：
    - `anchor-separated`：锚点被插入隔开；
    - `target-changed`：删除目标被插入改变或因删除缩短；
    - `anchor-lost`：锚点字符已被并发删除（目标被删改）；
    - `anchor-forged`：锚点标识从未签发（标识伪造）；
    - `anchor-mismatch`：删除锚点顺序颠倒。
  - 并发改动落在锚点外时不受影响（如文首插入后，原锚点仍可在新序列中定位）。
- **幂等与拒绝**：
  - 同一标识携相同载荷重传 → 复现首次确认的文本、修订与落点，**不新增修订**；
  - 标识复用但载荷不同（409）、未来修订（409）、越界或长度不符的删除（422）
    → 拒绝且规程文本与修订保持不变。
- **原子持久化**：每条补丁的规范化结果、新修订与标识序列随状态文件原子落盘
  （临时文件 + rename）；服务重启后从状态文件恢复历史、幂等记录、`seq` 与已退役标识，
  仍可按历史转换旧修订上的合法补丁，并继续受理重启前锚点的受保护补丁。
  旧版状态文件（无 `seq`）按当前全文重建序列，无锚补丁/幂等/历史变换行为不变。
- **维护重启**：`POST /api/admin/restart` 返回 202 后进程以约定退出码 42 退出，
  由 `scripts/serve.sh` 守护重新拉起（Docker 即以此方式启动）；
  `GET /api/health` 的 `bootId` 在每次进程启动时改变，供验收证实真实跨进程恢复。
- **健康状态**：`GET /api/health`。

## 运行

### 本地

```sh
sh scripts/serve.sh          # PORT=8080 DATA_DIR=./data 可通过环境变量覆盖
node --test test/            # 单元测试
APP_URL=http://localhost:8080 sh verify/run.sh   # 完整验收（未检测到服务时自动守护启动）
```

### Docker Compose（推荐）

```sh
HOST_PORT=8080 docker compose up --build --abort-on-container-exit --exit-code-from verify
echo $?                      # verify 的退出状态即验收成败
docker compose down
```

- `app`：页面、接口与健康状态，宿主机端口由 `HOST_PORT` 配置（默认 8080），
  状态持久化在命名卷 `app-data`；通过守护脚本启动以支持进程内维护重启。
- `verify`：等待 `app` 健康后执行 `verify/run.sh` —— 在业务检查之间穿插
  接口冒烟、代码测试（`node --test`）与构建检查（`node --check`），
  实际复核：同位并发插入的收敛文本、删除段内插入的保留结果、
  受保护补丁在并发改动后的接受与各类拒绝（隔开/删改/伪造）、
  **真实进程重启后的锚点与最近结论恢复**、以及旧式无锚补丁的回归；
  全部完成即退出，退出状态如实表示验收成败。

## 接口一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/health` | 健康状态（含本次进程 `bootId`） |
| GET | `/api/documents` | 草案列表（标识与当前修订） |
| POST | `/api/documents` | 建立草案 `{ id?, text }` → 201 |
| GET | `/api/documents/:id` | 全文、修订号、字符标识序列与最近结论 |
| POST | `/api/documents/:id/patches` | 提交补丁（旧式 / 受保护）→ 200 确认结果 / 4xx 拒绝 |
| POST | `/api/admin/restart` | 维护重启：202 后进程退出并被守护脚本重新拉起 |

确认结果：`{ revision, text, landing, normalizedOps, duplicate }`。

## 目录结构

```
src/transform.js   OT 转换与应用（纯函数）
src/document.js    文档：载荷校验、标识序列、锚点定位、幂等、转换、确认
src/store.js       文档集合与原子持久化
src/server.js      HTTP 接口、维护重启与静态页面
scripts/serve.sh   服务守护：退出码 42 时重启，信号转发不留孤儿
public/            补传确认终端页面（批准稿选择 → 锚点 → 受保护补传）
test/              单元测试（node --test）
verify/            验收编排（run.sh）与业务检查（acceptance.mjs）
```
